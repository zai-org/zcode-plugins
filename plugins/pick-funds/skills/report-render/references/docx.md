# DOCX 的失败模式

`pitfalls.md` 记的是 reportlab 那条路上的静默失败。这一份记 DOCX：**Word 打不开的
文件**、**看起来打开了其实换了字体的文件**，以及**分页归 Word 之后哪些检查不再成立**。

体例与 `pitfalls.md` 相同：每条先写症状，再写原因，再写修法。写在这里的每一条都是
「写文件的那个进程自己看不出来」的那一类。

## 一、Word 直接拒收：元素顺序

**症状**：Word 弹「Word 在文档中发现无法读取的内容」，然后要么修复、要么什么都不显示。
LibreOffice 常常照样打开，所以只在 LibreOffice 里试过等于没试。

**原因**：OOXML 的 `w:pPr` / `w:rPr` / `w:tblPr` / `w:tcPr` / `w:sectPr` 的子元素是
**有序序列**，不是集合。顺序错一个，schema 就不再匹配，Word 按无法读取处理。顺序既
记不住也猜不出来（`pStyle` 在 `keepNext` 前，`shd` 在 `spacing` 前，`jc` 在 `spacing`
**后**，`sectPr` 在 `w:pPr` 的最后）。

**修法**：不要在调用点手拼 XML。`fin_report.ooxml` 里每个有顺序的元素都有一个知道顺序
的构造函数，调用方只传关键字参数。这条不是风格建议——本后端建出的**第一份**文档就
栽在这里：`_break_after_cover` 把 `<w:pageBreakBefore/>` 插在了 `<w:pPr>` 的最前面，
于是 `pStyle` 落到它后面，schema 报
`Element 'pStyle': This element is not expected`。页面上看不出任何异常，因为根本没到
渲染那一步。现在补页面分隔要走 `ooxml.page_break_before()`，它知道那个槽位在哪。

**怎么提前发现**：把 ISO-29500 的 `wml.xsd` 路径放进 `FIN_REPORT_WML_XSD`，
`verify.py` 就会逐个部件做 schema 校验。schema 不随本包分发，所以默认关闭；但它是
「Word 到底打不打得开」唯一可自动化的近似，值得在有这个文件的机器上常开。

## 二、中文换了字体：`w:eastAsia`

**症状**：文档正常打开、文字都在，但整篇中文是另一种字体——通常是宋体那类衬线，
而房屋风格是无衬线。

**原因**：Word 解析中文走 `w:rFonts` 的 **`w:eastAsia`** 属性，`w:ascii` / `w:hAnsi`
只管拉丁字符。只设后两个，中文就落到文档主题的东亚字体上。

**这是 DOCX 版的「空白中文 PDF」，但轻一档**：PDF 缺嵌入字体是整页空白（致命），
DOCX 缺 `eastAsia` 只是替换（难看）。正因为不致命，它才更容易发出去。

**修法**：所有 run 走 `ooxml.run_props()`，它总是同时设 `ascii` / `hAnsi` /
`eastAsia` / `cs`。`verify.py` 会逐个 run 检查含中文却没设 `eastAsia` 的，判失败。

**字体选谁**：默认 `Noto Sans SC`，与 PDF 那条路嵌入的是同一个家族——一份报告和它的
Word 版是同一种字面。

这里**不嵌入字体**，只写字体名，读者机器上没有这个名字就替换。第一版按「读者多半用
Windows Word」把默认设成了 `微软雅黑`，那是错的：**本插件运行的环境里装的是
`/usr/share/fonts/truetype/chinese/` 下的 Noto Sans SC / Noto Serif SC，根本没有
微软雅黑**。写一个环境里不存在的字体名有两个后果——与 PDF 版长得不一样，以及**转换出
来的 QA 页面渲染的是替换字体**，于是视觉验收看的是一份谁都没写过的文档。

`verify.py` 因此在转换前检查所设字体在本机是否可解析（`fc-list`，没有就扫字体搜索
路径），解析不到就警告：那份逐页图的断行、列宽和总页数都是替换字体的，只能用来看
结构。**确知读者是 Windows 内网名单**时用 `DocxReport(..., font="微软雅黑")` 覆盖，
并接受 QA 渲染不代表最终观感。

**为什么不嵌入**：OOXML 支持 `w:embedRegular` 嵌入字体，一劳永逸解决所有读者的字体
问题，但一套中文静态字重约 10MB，两个字重把一份十页备忘做成 20MB 的 Word 文档。
不做，是权衡后的选择，不是遗漏。

## 二之二、标签不要画底色（2026-08-27 实测）

**症状**：读者反馈"tag 看不清"。

**原因**：那一批 Word 交付物是手搓 python-docx 建的，标签渲染成
`<w:color w:val="FFFFFF"/>` + `<w:shd w:fill="E7F3EC"/>`——**白字压在近乎白的浅绿底
上**。同一份文件里 132 个标签全是这个形状。

**修法**：标签是**有颜色的上标文字**，不是底色块。颜色由 `theme.CHIP` 按类别固定
（披露=深绿、测算=金、预期=蓝、推断=橙、媒体=灰），`chip()` / `tagged()` 是唯一出口。
画底色有两重损失：底色不是政策定义的颜色，而前景色同时不再承载类别。`verify.py` 现在
对带 `w:shd` / `w:highlight` 的标签 run 判失败。

## 二之三、`\n` 不是换行，`w:sz` 不是点数（2026-08-27 第三轮实测）

这两条都出自**本后端自己**建的交付物，症状分别是封面出现豆腐块和"整份文件被 Word 修复"。

**`\n` 在 `w:t` 里不是换行。** OOXML 没有换行字符，换行是 `<w:br/>` 元素。PDF 那条路
吃得下 `"2025E 算力市场\n(亿美元)"`——这个字符串就在本技能的 KPI 示例里——于是 DOCX
把它原样写进 `w:t`，封面上印出 `26H1归母净利润□同比-1.95%`，四个 KPI 标签全是这样。
`ooxml.run()` 现在把文本按 `\n` 切开、中间插 `<w:br/>`，作者侧照原样传即可。

**`w:sz` 是半点数，且必须是整数。** 类型是 `ST_HpsMeasure`，而排版比例里存的是真实
点数（来源条目 8.8pt、注释 7.6pt、表格 8.3pt），乘 2 直接得到 `w:val="17.6"`。
**schema 拦不住**——`ST_UnsignedDecimalNumber` 的底类型是 `xsd:decimal`，所以两份实测
文件各带 514 / 534 个这种值却通过了 schema 校验。Word 只写整数，读者拒收这个属性就会
触发修复，而**修复正是书签与底纹消失的地方**。`run_props()` 现在四舍五入到整半点，
`verify.py` 逐部件扫非整数值并判失败。

## 二之四、精确行高会被文档网格吃掉

**症状**：所有按"每段高度确定"算出来的落点——封面单页预算、尾块放置——在 Word 里都不成立，
而 XML 看起来完全正确。

**原因**：`w:sectPr` 里的 `<w:docGrid w:linePitch="…"/>` 让 Word 把每一行**吸附到文档网格**，
除非该段落显式退出。`w:snapToGrid` 的默认值是开，所以 `w:line ... exact` 会被网格改写。

**修法**：凡是设了精确行高的段落，同时写 `<w:snapToGrid w:val="0"/>`。`ooxml.paragraph()`
现在自动配对，`selftest` 断言两者数量相等——少一个就说明有段落的高度是可被网格改写的。

**顺带一条槽位教训**：`snapToGrid` 在 CT_PPrBase 里排在 `tabs` **之后**，我第一次放在它前面，
schema 报 `Element 'tabs': This element is not expected`。这已经是同一个函数里第二次靠 schema
校验发现顺序错误（第一次是 `pageBreakBefore` 抢在 `pStyle` 前）——**顺序不要靠记，靠校验**。

## 二之五、固定行距会把图裁成一条缝

**症状**：读者说「文字盖住了图」。实际是图只露出一条约 15.5 磅高的横切面，图该占的位置
被上下文的正文行占着。

**原因**：正文的行网格是 **15.5 磅 + `lineRule="exact"`**，而它定义在 `docDefaults` 里。
于是**不写 `w:spacing` 的段落会继承它**——包括放图的那个段落。嵌入式图片在固定行高的行框
里会被**裁到行框大小**，一张 60mm 的图就只剩 15.5 磅。图片元素本身抵抗不了这件事，只有
段落能退出。

**这条最难自查的地方是它源于"什么都没写"**：XML 里看不到任何可疑属性，看不到才是病征。
实测一份交付物**12 个含图段落全部**如此。

**修法**：放图的段落显式写 `w:line="240" w:lineRule="auto"`（`auto` 的单位是 240 分之一行，
240 就是单倍行距，**不是 twips**）。**不能靠"省略 w:spacing"**——省略正是继承，也正是缺陷
的来源。`ooxml.paragraph(..., auto_line=True)` 负责这件事，`rep.figure()` 已经带上。
`verify.py` 逐个含 `w:drawing` 的段落检查行距规则，不是 `auto` 就判失败：**"没有
spacing 元素"要读成失败，不能读成默认**。正文文字的行网格不动——版式风格不受影响。

## 三、引用：书签 + 超链接锚点，不是 `REF` 域

**症状**：`[n]` 在 Word 里点不动，或者点了跳空；再或者引用位置显示成空白/`Error!
Reference source not found`。

**原因**：三种不同的东西容易混：
- `w:hyperlink w:anchor="ref3"` —— 跳到同文档内名为 `ref3` 的书签。**这是本包用的。**
- `w:hyperlink r:id="rId7"` —— 外链，`r:id` 必须在 `word/_rels/document.xml.rels`
  里有对应关系条目，且该条目**必须带 `TargetMode="External"`**。漏了这个属性，
  Word 判整包损坏，不是「链接失效」而是「文件打不开」。
- `REF` 交叉引用域 —— 需要读者按 F9 或 Word 自行更新域才显示。**本包不用**：域未更新
  时读者看到的是空的或过期的引用，而引用政策要的是「读者点得动、点到对的地方」。

**修法**：`[n]` 只从 `rep.refs.cite()` 来（返回标记并登记条目，两者不可能不一致），
Sources 条目里的 `<a name="refN"/>` 由 `refs.lines()` 自带，写盘时变成
`w:bookmarkStart`/`w:bookmarkEnd` 对。`verify.py` 两头都查：有 `[n]` 却没有任何
`w:anchor` 判失败（标记是死文本），有 `w:anchor` 却没有同名书签也判失败（点了跳空）。

**让链接长得跟 Word 自己写的一样。** 规范上 `w:hyperlink w:anchor` + 同名书签就够了，
但实测报回来的就是"点不动"，所以不在没有收益的地方与 Word 的产出不同：现在每个链接带
`w:history="1"`，链接内的 run 带 `w:rStyle w:val="Hyperlink"`（styles.xml 里定义了这个
**字符**样式——声明成段落样式 Word 会忽略引用），书签也不再是零长度：`bookmarkStart`
包住条目自己的 `[n]` 文本再 `bookmarkEnd`。零长度书签是合法的，也是本后端最初的写法，
但 Word 的交叉引用目标从来都包着文本，而丢弃空书签的读者会让引用看起来像个死链接。

**书签名与 `w:id` 都要唯一**。`w:id` 重复 Word 会修复文件；名字重复则跳转不确定。
`Package.ident()` 是全文档唯一计数器，图片的 `wp:docPr id` 也从它来——那个 id 重复
同样触发修复。

**2026-08-27 实测的三个致死写法**，全部出自手搓 python-docx，症状统一是"正文溯源点不动"：

1. **`w:bookmarkStart` 写在 `w:pPr` 之前**。`w:pPr` 必须是 `w:p` 的第一个子元素，抢在
   它前面就出了 schema，Word 在修复过程里把书签丢掉——`[n]` 看着像链接，点了没反应。
   两份文件里 17 个和 12 个书签**全部**是这个写法。
2. **`w:id` 重复**（实测 id 4、5 各出现两次）。配对靠 id 不靠名字，重复即歧义，后一个
   书签被丢。
3. **锚名拼错成 `ref[1]`**（"ref" + "[1]" 直接拼），指向不存在的书签。

`verify.py` 三条都查。`ooxml.bookmark()` + `ooxml.paragraph()` 三条都写不出来。

**每一处 `[n]` 都要在 `w:hyperlink` 里，不是"大部分在"。** 2026-08-27 第二轮实测：
一份手搓交付物把正文 24 段的标记包成了链接，而**十条图注/表注里的标记全是死文本**，
另有 18 段正文也是。读者的体验是"正文能点、每张图下面都不能点"——而图注恰恰是图表
**唯一**能承载溯源的地方，因为图里的数字在 PNG 里。`verify.py` 现在逐段扫：不在
`w:hyperlink` 里的 `[n]` 一律判失败（来源条目自己开头的 `[n]` 是标签，豁免）。

**图注里别用散文交代口径。** 同一批文件的图注写「…；比率均为本报告测算。」，全篇没有一个
`[测算]`。政策对**表格单元格**有明文——「在表格注释里用一句话交代口径不算标注，读者没法把
一句话映射到单元格上」；图表是政策没写到的情形，因为数字在图里、没有单元格可标，注释是
唯一的落点。`verify.py` 对这种注释报**警告**而不是失败：政策在单元格上表过态，在图表上
没有，这一层不替政策把规则加硬，但会把这个歧义说出来。

## 四、页眉页脚与页码

**症状**：每一页都印「第 1 页」；或者封面顶着正文的页眉页脚；或者正文页什么furniture
都没有。

**原因**：DOCX 的页眉页脚是**独立部件**（`word/header1.xml`），由 `w:sectPr` 里的
`headerReference` / `footerReference` 引用，按 `w:type` 分 `default` / `first` /
`even`。页码必须是 `PAGE` **域**——手打的数字不会递增。

**修法**：
- 封面**不引用任何**页眉页脚：它是自己的一节（见下一节），而一节不写引用时只从**前一节**
  继承——封面是第一节，所以什么都不继承，页码自然从正文起。`w:titlePg` + 一对故意留空的
  first-page 部件是另一条合法的路，本后端用过，在封面并入正文那一节的那几版里是唯一的
  路；换成独立封面节之后它就是多余的一层。两条路都不走的话，封面继承 default，标题块
  下面印出「第 1 页」——这正是 PDF 那条路反方向踩过的坑：模板注册顺序错了，正文页穿着
  封面的家具（见 `doc._templates`）。
- **零页边距的节里绝不能引用页眉页脚**：那一节的 header 会画在纸的边缘上。`verify.py`
  对此判失败。
- 页码走 `ooxml.field_run(ooxml.PAGE_FIELD, "1", …)`，`w:fldSimple` 带一个缓存值，
  不求值域的阅读器也能显示数字，Word 与 LibreOffice 打开时会重算。
- **域指令必须写全格式开关**：`PAGE_FIELD` 是 `" PAGE \* arabic \* MERGEFORMAT "`，
  不是裸的 `" PAGE "`。**WPS**（相当一部分读者用它打开 Word 文件）不认 section 上的
  `w:pgNumType` 格式，遇到裸指令会把域代码本身印在页脚上——读者看到的是
  `PAGE \* arabic \* MERGEFORMAT` 而不是页码。Word 自己插入页码时写的也是这一串，
  所以写全没有代价。
- `verify.py` 检查：default 页眉页脚都被引用、有 `w:titlePg` 就必须有 first 页脚、
  零页边距的封面节不得引用页眉、任一 footer 部件里必须出现 `PAGE`。

## 五、封面：通版色带靠「自己一节 + 一格表」，约束只留必须的那几条

**现在的做法**，全部在 `word.py` 的 `cover()` 与 `_kpi_strip()` 里。封面是**它自己的一节，
页边距全 0**（`Page.cover_sect_pr`），四块：

1. **色带**——一张**单格表**，宽度就是纸宽，单元格 `w:shd` 深蓝、`tcMar` 左右各 18mm、
   `vAlign=top`，格内四段：精确行高 **96pt** 的空段（`_BAND_TOP_PAD`）→ 标题 27pt 白字 →
   副标题 13.5pt `#D6E2F0` → 精确行高 **40pt** 的空段（`_BAND_BOTTOM_PAD`）。
   表格下边框 **1.5pt 金色**，通版。行高不设 `trHeight`，随标题行数自然增减。
2. 一段空的 `Note`，`space_after = 40mm`；
3. 元信息段——每行一段，10.5pt 灰字，`w:ind` 左右各 18mm 缩到文本列；
4. KPI 条——两行表，`tblInd` 缩到文本列，上金线下细灰线，数值 18pt 深蓝、标签 8.5pt 灰。
   **它上面不留间距**：KPI 是元信息的注脚，中间掉一段空的读起来像两块不相干的面板。

最后一段空段落带 `sectPr` 收掉封面节。**节分隔本身就开新页**，所以封面没有分页符，全文
只剩「来源前」那一个 `pageBreakBefore`。封面节不引用任何页眉页脚，页码自然从正文起——
不需要 `w:titlePg`，也不需要那对故意留空的 first-page 部件。

**为什么色带必须是表格，不能是带底纹的段落。** 通版要靠零页边距的节：段落底纹填的是
「左缩进到右缩进」，在没有页边距的节里这一段就是整张纸。但**文字得从两边缩进来**——
左边可以用制表位（`w:tab` 只挪文字，`w:ind` 会把底纹一起挪走），**右边没有对应物**：
除了 `w:ind` 没有别的办法把折行位置收进来，而 `w:ind` 一用通版就没了。于是纯段落方案的
标题会一路顶到纸的右边缘。单元格的 `w:tcMar` 两边都能缩，而填充照样铺满整格——这是
唯一同时成立的做法。Word 会给无边框单元格画非打印的**虚线网格线**，但**填了色的格子上
看不到**，所以色带这一格不会有；KPI 那两行仍然有，它们不打印。

**留白只能是「空段落 + 精确行高」，不能是 `space_before`。** 段落底纹覆盖的是**行框**，
不覆盖段间距——给标题段设 `space_before` 会在色带上方印出一条**白缝**。这条踩过两次，
第二次的症状是读者说「标题上面只有一小块，很奇怪」：当时既没有顶部留白段，色带又只有
文本列那么宽，于是深蓝看起来是标题左上角的一小块贴纸而不是一条通栏。

**色带高度不由任何数字声明。** 顶部 96pt + 标题实际行数 × 行高 + 副标题行 + 底部 40pt，
单行标题约 67mm、两行约 80mm。作为参照的那版把色块钉成 exact 77.6mm，块内文字只占
38.8mm，副标题下面空着 38.8mm 深蓝——那正是「整个排版往上压缩」在说的东西。纵向节奏
照它，那段死区不照。

**为什么约束这么少**：这是一份 Word 文件，分页与折行归读者的 Word 管，我们**声明不了**
的东西就不要假装声明。下面「试过又退回」那一节记的就是硬声明的代价。

**排版上仍然是硬的三条**（违反了封面会散）：

- **段落底纹只覆盖行框**，不覆盖 `spaceBefore`/`spaceAfter`。色带的厚度来自行高与段内
  留白，不来自段间距。
- **底纹与单元格填充都只填到「缩进以内」**，靠零页边距的节才铺到纸边；正文那一节里
  做不到通版。
- **表格边框必须显式写成 none**（`ooxml.table` 本来就这么做）。默认边框每边约 8 twips，
  MS Office 会据此算出超过页高的总高、在封面后挤出一张**空白页**——WPS 宽容，MS Office 严格。

**KPI 表的虚线框是 Word 的屏幕网格线，不是我们画的边框。** Word 给每一个无边框单元格画
非打印的虚线（查看→网格线，可关）。它不会印出来。曾经为消掉它把 KPI 条改成两段带居中
制表位的段落，代价见下——现在接受这个屏幕现象，换回表格。

### 退回来的那一层，以及为什么退

零页边距的独立封面节与整页宽的表都留下了——它们是通版的**机制**，上面那一节讲了为什么
非它不可。退掉的是加在它们上面的**约束层**：**按实测宽度逐档选字号 + 把尾块"放置"到
页高 80% 的单页预算**（`_TITLE_STEPS` / `_COVER_BOTTOM` / `_META_DROP_MIN` / `_fit_size`，
配一条「会溢出到第 2 页就拒收」）。

它修掉了它针对的症状，代价是把封面变成**一个约束系统**：字号不再是常数、垂直落点由算术
决定、封面的容量成了会拒收的闸门。而这些算术全部建立在「每段有多高」的**估算**上——
Word 的实际折行我们看不见，估算一偏，所有落点跟着偏。回退掉的就是这一层。

留下的教训，写在这里而不是写在代码里：

- **「往上压缩」有两种**。一种是文字被顶在过大的色块顶部（固定 4400 twips 的色块装两行字，
  副标题下空 45mm 深蓝）；另一种是整张封面被顶在页面上部（固定间距让内容止于页面 42%）。
  现在靠常数搭配避免——27pt 标题 + 40mm 空隙 + KPI 条，落点与 PDF 封面同形。
- **估算宽度对中文够用，对拉丁低估约 9%**。当时一个 39 字符的英文标题在 27pt 下实宽 595pt、
  列宽只有 493pt。长英文标题在这一版会折成两行——这是已知的、可接受的表现，不再为它降档。
- **居中制表位上的文字不会折行，只会撞上邻居**，这是当初不敢用段落做 KPI 条的相反理由：
  换成表格后，单元格会自己折行，撞不上。
- 零页边距的节里，段落边框会一直画到纸边；表格也会。KPI 那两条规则线因此要靠 `tblInd`
  缩回文本列，否则线通版而它上面的元信息在列内，看起来像两套版心。

**看不见就别猜。** 本机没有 LibreOffice，无法把 docx 渲成图。诊断这些时用的是"按
OOXML 语义模拟 Word 版面"的临时脚本——**它第一版不做换行**，于是把一个 Word 里正常
折行的标题画成了溢出，害我把"标题溢出"写进了结论。给模拟器补上折行之后，那条结论
撤掉了。**模拟器不是渲染器**：它能看出色带厚度、缩进、空隙、豆腐块，看不出折行与分页。
上面那三版被回退，一半原因就是它们信任了模拟器算得出、Word 才说了算的东西。

### 通版：能做到，但只有一条路

**症状**：PDF 封面那条通版深蓝带，在 DOCX 里两侧留白，读者说「背景还是只有一小块」。

**原因**：PDF 是画布，色带用 `canvas.rect` 画到纸边。DOCX 没有画布；`w:shd` 填的是
**缩进以内**，在有页边距的节里就是文本列。

**修法**：零页边距的封面节 + 填满这一节的单格表（见上一节）。另一条路是**浮动图形**
（`w:pict` / DrawingML 锚定形状），不用：读者第一次编辑就会把它挪位，而 DOCX 的存在意义
就是可编辑，一个一编辑就散架的封面是负资产。

## 六、对照 PDF：哪些约束在 DOCX 上成立、怎么成立

这一节存在的理由是：**「PDF 有的检查 DOCX 也有」是一句需要逐条核对的话**，不核对就
会有一半在这条路上悄悄失效（图例位置那条原本就是——见下）。

| PDF 侧的约束 | DOCX 侧 | 怎么做到的 |
|---|---|---|
| 五标签只能由 `chip()`/`tagged()` 印 | 同 | `theme.chip()` 抛错，`inline.py` 渲染成上标 run |
| 图例必须有、只列用到的标签 | 同 | `rules.legend_problem()`，两个后端共用 |
| 图例在文首或封面页脚，不在小节里 | **另写了一份** | 共用检查靠 running header 判断"上方只有页面家具"，而 DOCX 页眉在独立部件里，正文没有 chrome，那个检查恒真。改用 `_docx_check_legend_position`：图例必须是所在 block 的第一行 |
| 同比/环比/占比 列整列无标签 → 拒收 | 同 | `rules.untagged_columns()` |
| 派生值裸奔 / 手打标签 / 值重复印 / 来源写接口名 / 域名级 URL | 同 | 复用 PDF 的纯文本检查器，位置词从 page 改写成 block |
| `[n]` 可点击 | 同 | `/Link` 注解 → `w:hyperlink w:anchor` + `w:bookmarkStart`，两头都查 |
| 字体缺失 | 同类 | 未嵌入 → 含中文 run 缺 `w:eastAsia`；另外转换前查所设字体本机是否存在 |
| 缺字形 `.notdef`（⊠） | **不适用** | DOCX 会照实渲染 emoji，所以改查分级图标本身 |
| **空白页** | **结构那半有，且不需要 LibreOffice** | 一个分页符与下一个之间没有正文/图/表 → 判失败；文末分页符 → 判失败。**"几乎空"那半**（整块被推走留下大片空白）需要排版引擎，只在转换出的 PDF 上量 |
| 表格宽度归一到文本列 | 同，且成品复查 | 列宽走 PDF 同一个分配器；`_docx_check_tables` 再在文件上核对 grid 合计与文本列的差值。**Word 不会缩表**，超宽就把最后一列挂到页边距外 |
| 表头跨页重复 | 同 | `w:tblHeader`（对应 `repeatRows=1`） |
| 表格无竖线、斑马纹、深蓝表头 | 同 | `ooxml.table` 显式把竖线写成 `none`，不留给读者的默认表样式 |
| 短行补齐 | 同 | reportlab 给缺格补空单元格，DOCX 侧照样补——不补的话同一份输入在 Word 里是"半截行"，在 PDF 里是整行。`_docx_check_tables` 还会查 grid 与每行格数 |
| 页码是域、封面不带页码 | 同 | `PAGE` 域 + 封面自成一节且不引用任何页眉页脚 |
| 硬分页只允许封面后与来源前 | 同 | 封面后是**节分隔**（自带开新页），来源前是唯一的 `pageBreakBefore`；两者都算页面边界，多出来的会被空白页检查抓到 |
| 图放不下就按剩余高度收缩（`_FittedFigure`） | **不适用** | 分页在读者机器上发生，收缩没有对位物；图按密度档宽度直接放 |
| Sources 列表实测行距选最省页的一档 | **不适用** | 同上，直接用最松的一档 |
| 墨量下限 / 页脚空隙 / 末页 stub / 逐页视觉验收 | **只在转换出的 PDF 上** | 缺 `soffice` 就 exit 3，明说没量 |
| 断行处 `[标签]`/`[n]` 被切两半、行首禁则 | **故意不做** | 断行是 Word 做的，本包看不到结果；在源文本上跑会永远通过，读起来像已排除，比不查更糟 |

## 七、分页归 Word，所以这些检查不再成立

**症状**（其实是没有症状，这正是问题）：一份 DOCX 走完 `verify.py` 报 OK，然后打开
一看，第 3 页只有一行、图 5 被整块推到下一页、末页只剩一条来源。

**原因**：`_FittedFigure` 的按剩余高度收缩、Sources 列表的实测行距、页脚空隙、墨量、
末页 stub —— 全部需要知道分页结果。DOCX 的分页在读者那台 Word 上才发生。

**修法（唯一诚实的一条）**：装 LibreOffice。`verify.py` 见到 `soffice` 就把 docx 转成
PDF 落进 QA 目录，然后**复用 PDF 那一整套几何检查**并出逐页 PNG 供视觉验收；见不到
就 `status="pagination_unavailable"`、**exit 3**，并明说版面从未被测量。

**注意 PDF 那条路不需要 LibreOffice**，两者不要混为一谈：reportlab 直接写出 PDF，
`pypdfium2` 直接把页面栅格化成 PNG，全程没有外部转换器。LibreOffice 在本仓库只出现在
两处——`xlsx-author` 的公式重算，和这里的 DOCX 分页。它是这个环境里既有的、可以依赖的
组件；DOCX 之所以需要它，是因为**只有排版引擎知道页在哪断**。

**转换出来的 PDF 是 Word 的近似，不是 Word。** 域（`PAGE`、目录）与字体替换是已知的
分歧来源：LibreOffice 求值域的方式与 Word 不完全一致，字体缺失时它自己挑替代品。所以
逐页图能定的是「这一页是不是空的、是不是半空的、图有没有画出来」，定不了「Word 里会不会
正好多断一行」。接受版面时把这句一起记进 `layout-review.md`，不要把近似当成终审。

这条退化路径照 `xlsx-author/scripts/recalc.py` 的先例设计，理由也一样：那个脚本早期
版本对每种结果都返回 0，于是 `&&` 链把一份满是 `#REF!` 的工作簿当成通过。**exit 3
不是通过**——把 `未经视觉验收(已过结构检查)` 记进 `layout-review.md`，并在交付消息里
说出来。

另外两条 PDF 检查在这里**故意不做**：断行处 `[标签]`/`[n]` 被切两半、行首禁则。它们
存在是因为 reportlab 的 CJK 断行器是日文的（见 `fin_report.cjk`）；这里断行是 Word
做的，本包看不到结果。在源文本上跑这两个检查会永远通过，读起来像是已经排除了这类
缺陷——那比不查更糟。

## 八、交付卫生：转出来的 PDF 也是脚手架

`--render` 目录里现在多了两样东西：LibreOffice 转出的 `报告.pdf`，和它的
`profile/`。两者都是脚手架，跟 `qa/p01.png`、`_chart_meta.json`、生成脚本一样，
**不进交付目录**。Step 5 删掉整个 `BUILD` 目录就一并清掉了。

**特别注意那份转出来的 PDF**：它和交付物同名不同后缀，躺在同一棵目录树里，是最容易
被误当成「顺手也给了个 PDF 版本」的东西。它是 QA 中间产物，字体可能已被 LibreOffice
替换，不能交付。用户要 PDF 就用 `Report` 重新建一份。
