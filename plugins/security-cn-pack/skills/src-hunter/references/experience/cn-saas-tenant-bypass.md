# SaaS 多租户越权实战 playbook（真实案例沉淀）

> 视角：国内 SaaS / 企业云服务（教育、协同、客服机器人、AI 能力平台等）。
> 来源：实战案例复盘——多租户隔离缺陷是国内 SaaS 最高产的洞型，危害定级高（跨企业数据），且请求形态正常、WAF 零告警。
> 纪律：本文是测试方法论；所有验证只用自己注册的账号，拿到的他企数据只截图证明不下载不外传。

---

## 1. 攻击面模型：SaaS 多租户的四个断点

租户隔离设计假设："请求方身份、租户标识、资源归属 三者始终一致"。实际常见四个断点：

| 断点 | 缺陷 | 测试 |
|------|------|------|
| **认证断点** | 存在 guest/游客/匿名登录接口，零凭据换取合法 token | 找 `/guest/login`、`/sso/anonymous`、开放接口下发的 JWT |
| **归属断点** | 租户标识参数（fid/orgid/cid/companyId）可改，且不校验"该标识是否属于当前身份" | 换 fid 请求他租户资源 |
| **绑定断点** | 资源接口校验了 token 有效性，但 token 里的身份与目标资源不绑（Host 换了也能通） | token 换 Host/网关域名复用 |
| **泄露断点** | 配置类/诊断类接口回显 appKey、secret、内部 endpoint | 遍历 `/verify`、`/config`、`/info` 类接口 |

## 2. 测试流程（四步）

### Step 1 拿合法身份
- 正常注册企业账号（自己控制的企业 A）
- 同时探测：是否存在 **guest/游客登录**（POST 任意身份字段换取 token）——存在则零凭据起点

### Step 2 摸清租户标识
- 抓包找所有请求里的**租户/机构参数**：fid、orgId、cid、schoolId、companyId、tenantId
- 记录它的取值规律（数字自增？雪花？哈希？）——数字自增 = 可遍历
- 看它出现在哪：URL、body、还是 token payload 里

### Step 3 三向替换实验
对每个资源读取/写入接口做三组对照（全部用自己控制的身份）：

```
实验1（水平）: 身份A + 资源A          → 基线（应成功）
实验2（水平）: 身份A + 资源B(他租户)  → 成功 = 跨租户越权
实验3（垂直）: 匿名/guest + 资源A     → 成功 = 认证断点
```

**附加变体**：
- Host 替换：A 域名的 token + B 租户的专属域名/网关——部分 SaaS 按 Host 路由租户但不验证 token 签发方
- 参数置空：fid 删掉或置空，看是否回落到"当前用户默认租户"之外
- 二级资源穿透：机器人/知识库/应用 ID 单独遍历（即使列表接口有隔离，详情/配置接口常漏）

### Step 4 危害定级
- 可读他企：机器人对话记录、知识库、通讯录、订单、AI 应用配置 = **高危**（企业数据）
- 可写他企：修改他企配置、伪造他企身份对外发消息 = **严重**
- 仅泄露 appKey 无后续利用路径 = 中危起步，继续追"appKey 可签名哪些接口"

## 3. 快速止损判断（省时间）

以下特征说明隔离是**双向闭环**，跨租户大概率打不通，尽早换目标：
- 资源接口只收 token 里的身份，URL/body 不出现任何租户参数（无注入点）
- 两个企业账号交叉实验全部双向失败（A→B 与 B→A 都不通）——**做满双向对照再下结论**，单向不通可能是数据本身不存在
- 企业网关按 SSO 域名硬绑定，换 Host 直接被网关层拒绝

## 4. 提交注意

- 报告里强调**跨企业边界**（"企业 A 的账号可读取企业 B 的 XX"），不要写成"未授权访问"——前者危害高一级
- 证据链：两个自己注册的企业账号信息 + 每步 HTTP 包 + 他企数据截图（打码）
- SaaS 厂商多按"租户隔离缺陷"内部定级，附上影响面估算（该租户参数空间大小）
