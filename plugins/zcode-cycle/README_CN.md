# Cycle for Zcode

Cycle for Zcode 是一个在本地运行、以证据为准入条件的 ZCode 交付插件。它将架构、
实现、功能审查、安全审查和最终裁决分离，并由确定性的 Rust 控制平面管理工作流状态、
候选文件、验证证据和交付。

## 1.0.11 支持范围

| 平台 | 状态 |
|---|---|
| Windows 11 x64 | 认证目标 |
| Linux x64（Ubuntu 22.04、24.04） | 认证目标 |
| macOS x64 / arm64 | 仅在原生构建通过后声明“兼容但未经测试” |
| Windows/Linux ARM64 | 不支持 |

认证会绑定发布凭据中记录的具体 ZCode Desktop 版本。ZCode 升级后，必须重新执行宿主
集成矩阵，原凭据才可更新。

该范围内有一项例外：**浏览器与无障碍门控仅在 Windows 上完成认证**。它们在 Linux 上
预期同样可用——实现是共用的，唯一与平台相关的部分已有测试覆盖——但尚未在该平台上被
实际观察运行过，而未经观察的条目不会被记为通过。Cycle 使用你机器上已安装的浏览器；
关于它会查找哪些浏览器、以及如何指定其他浏览器，参见
[浏览器指南](docs/guides/browser.md)。

## 安装

生产用户应仅在 `1.0.11` 被接纳并发布后，从 ZCode 官方公共插件市场安装。角色配置、
Hook 和本地守护进程都以你的权限运行，可信来源是其字节可被追责的前提，因此官方发布
是安全门槛。

开发和认证时，请在 Settings -> Plugins -> Create -> Add marketplace 中添加本地目录
市场，选择本仓库并安装 `zcode-cycle`。在每个受治理项目中运行
`/cycle:setup install`，新建 ZCode 会话，再运行 `/cycle:setup` 验证五个受管理角色配置。
主会话负责编排，各角色作为子 Agent 运行。
每次 Cycle 角色调度都必须有唯一的 Cycle 注册；绕过注册直接启动 Agent 会被拒绝。

要求：

- 支持插件的 ZCode Desktop；
- 插件进程可用 Node.js 22 或更高版本；
- Git，以及被治理项目所需的构建和测试工具；
- Windows x64 或受支持的 Linux x64；
- 当变更需要浏览器证据时，系统中有 Chrome、Edge 或 Chromium。

对应平台的 `workflowd` 守护进程包含在经过校验的插件制品中。运行时不会从远程地址
下载或执行二进制文件。

## 插件内容

- 五个显式项目角色配置：架构师、执行器、两名审查者和裁决者；主 ZCode 会话负责编排；
- 斜杠命令和五个工作流 Skill；
- 面向主会话的 `PreToolUse` 保护 Hook 与 `PostToolUse` 审计 Hook（ZCode 不会在被
  派发的 Agent 内运行这两者，因此约束角色的是其配置文件，而非这些 Hook）；
- 一个本地 stdio MCP 服务；
- 根据锁定的 npm 依赖图构建的自包含 MCP/浏览器桥；
- 平台限定的 `workflowd` 二进制文件、用户文档和法律声明。

## 权限与副作用

Cycle 只有在用户明确启动受治理运行后才会修改项目。

### 文件和 Git

- 普通对话、设置、架构和审查均为只读。
- `/cycle:setup install` 会在当前项目的 `.zcode/agents` 下写入五个受管理文件；修复、
  模型变更和删除必须使用对应的显式命令，且不会覆盖不属于 Cycle 的冲突文件。
- 每个角色都可以单独固定模型，账本记录的是该角色配置文件所固定的模型——Cycle 无法观测
  ZCode 的实际派发，因此该记录证明的是模型指派，而非推理本身。Cycle 只校验模型引用的
  **形式**：只有 ZCode 能解析提供商，并且它是在角色被派发时才给出答案。因此被固定模型
  的角色在首次成功启动之前会被报告为 `dispatch_unverified`，并且受治理运行会在开始前
  先探测每一个被固定的角色——这样，ZCode 无法解析的提供商只会让你损失几秒，而不是一整轮
  架构、执行和验证。这一限制不影响你自己的主会话。
- 执行器在隔离的 Git worktree 和声明的写入范围内修改文件，并可暂存和提交该 worktree
  的变更。
- 执行器并未被沙箱隔离：它持有编辑和 Shell 工具。真正约束它的是控制平面——除非你的项目
  仍停留在工作流开始时的修订版本且没有未提交的改动，否则拒绝冻结候选版本。逃逸出
  worktree 的改动会中止本次运行并被具名指出，而不会随候选版本一同交付。
- 控制平面冻结候选文件的精确字节，完成验证后只把获批路径提升到记录的基础修订。
- 导出、可能丢失数据的取消、外部浏览器来源和发布均需要用户明确决定。Cycle 不会绕过
  ZCode 的确认或安全策略。

### 命令执行

控制平面执行已验证计划中声明的验证命令。命令通过参数向量直接启动，而不是交互式
Shell；不安全操作符、被阻止的程序和破坏性形式会被拒绝。命令使用当前操作系统用户的
权限运行。请按 ZCode Terms 的建议在隔离的开发环境中使用，并人工审查高风险操作。

### 网络和浏览器

- Cycle 不包含遥测、账户服务、更新服务或远程后端。
- MCP 桥与守护进程仅通过本地认证管道或 Unix socket 通信。
- 托管浏览器使用隔离的临时配置。默认允许 loopback；任何外部来源都必须明确批准，
  之后浏览器请求会直接访问该已批准来源。
- ZCode 及用户选择的模型/提供商受各自条款和隐私政策约束。Cycle 不读取或保存模型
  凭据。

### 本地数据

工作流状态、防篡改账本、签名密钥、worktree、浏览器证据和项目记忆位于应用安装目录
之外：

| 平台 | 默认目录 |
|---|---|
| Windows | `%LOCALAPPDATA%\ZCode Cycle` |
| Linux | `$XDG_DATA_HOME/zcode-cycle` 或 `~/.local/share/zcode-cycle` |
| macOS | `~/Library/Application Support/ZCode Cycle` |

卸载插件不会删除这些审计数据。只有在完成必要备份并明确决定销毁数据后，才应单独删除
该目录。

## 交付流程

1. `/cycle:run auto|quick|full` 原样捕获用户的下一条请求。
2. 架构师生成与需求关联、范围有限的任务图。
3. 执行器在隔离 worktree 中实现并提交任务。
4. 控制平面冻结候选版本并运行强制 Gate。
5. Full 模式并行调用两名无 Shell 权限的独立审查者。
6. 裁决者根据原始请求、精确候选版本和原始证据作出判断。
7. 只有获批候选版本才会提升。拒绝会进入有上限的修复循环；中断后通过
   `/cycle:resume` 恢复。

更多信息见[用户手册](docs/USER_MANUAL.md)、[命令参考](docs/commands/reference.md)、
[威胁模型](docs/security/threat-model.md)、[发布校验](docs/releases/verification.md)，
以及每个版本据以衡量的[实机认证标准](docs/releases/zcode-live-certification.md)。

## 更新、回滚和删除

- 已发布版本不可复用。刷新市场后升级到更高的语义版本，运行
  `/cycle:setup repair`，并新建会话。
- 发布认证包含从上一公共版本升级、保留数据的回滚。较新的数据库 Schema 只能按文档
  以安全只读模式打开。
- 卸载前在每个已配置项目运行 `/cycle:setup remove`，然后在 ZCode 中删除插件。只有在
  不再需要账本、记忆、证据和恢复状态时，才单独删除数据目录。
- **这是 ZCode 的限制，而非 Cycle 的**：卸载会移除当前安装，但保留市场自身的镜像副本。
  详见下文。

## 已知的 ZCode 限制

以下均为宿主行为。Cycle 无法从插件内部改变它们，在此记录是为了让你在卸载后看到的
情况是可预期的，而不是令人不安的。

**卸载不会移除市场对插件的镜像副本。** 位于
`plugins/cache/<市场>/<插件>/<版本>/` 的已安装副本**会**被完整删除，该目录会被清空。
保留下来的是 ZCode 对市场源的镜像，位于你的 ZCode 配置目录下的
`plugins/marketplaces/<市场>/`：约 76 MB，比安装本身更大，因为它包含**每个**受支持
平台的原生守护进程，而不只是你的那一个。

请到正确的位置查看。卸载后去检查插件缓存的人会发现它是空的，从而以为删除已经彻底完成，
而那 76 MB 在别处。

ZCode 的确认对话框声称会移除"插件的缓存文件、数据目录和任何已保存的配置"，并且
"无法撤销"。市场镜像不在其中，你的 Cycle 数据目录也不在——对话框所指的是 ZCode 自己
位于 `plugins/data/` 下的插件数据目录。请把该措辞理解为描述"当前安装"。

保留下来的副本是惰性的：它不在 `installed_plugins.json` 中，因此不会被加载，卸载后
也不会有守护进程从中运行。它只占用磁盘空间，别无影响。

有一个进程会在卸载后继续存在，直到 ZCode 重启：任何已打开会话中的插件 MCP 服务器。
ZCode 不会停止它。它是惰性的——其文件已被删除，因此该会话中的任何 Cycle 调用都会以
`required native package ... is not installed` 失败，也不会启动守护进程。卸载后重启
ZCode，它就会消失。

**更新同样会保留旧版本的已安装副本。** 从插件市场更新时，新版本会安装在旧版本旁边的
`plugins/cache/<marketplace>/zcode-cycle/<version>/` 下，旧文件夹保持完整。它同样是惰性的：
`installed_plugins.json` 只列出新版本，旧版本中不会运行任何内容。如需回收空间，可删除旧
版本的文件夹。

**更新会停止旧版本的守护进程。** 守护进程会比 ZCode 会话存活更久，因此更新后旧守护进程
通常仍在运行。从 `1.0.11` 起，新插件会按其服务的数据目录找到它，在其版本较旧时将其停止
并启动自己的守护进程；它绝不会停止比自身更新的守护进程。`1.0.10` 及更早版本做不到：
从这些版本更新后会停在 *"workflowd did not become healthy within 15 seconds"*，直到手动
停止旧守护进程（任务管理器，或 `Stop-Process -Name workflowd`）或重启 Windows。

若要回收这部分空间，请在卸载插件后再在 ZCode 中删除该市场本身。Cycle 刻意不替你删除：
该镜像及其注册表属于 ZCode，插件伸手进宿主的注册表去擦除条目，比它所回收的磁盘空间
是更严重的错误。

你的审计数据是另一回事，**不会**被卸载移除。Cycle 控制平面位于插件目录之外，正是为了
让删除插件无法摧毁账本、记忆、证据和恢复状态。只有在你不再需要该记录时，才自行删除
那个目录。

## Windows SmartScreen 与未签名的守护进程

Cycle 附带原生控制平面守护进程 `workflowd.exe`，**它没有使用 Authenticode
证书签名**。每个发布中的 `authenticode.json` 都将其记录为 `NotSigned`，并且发布
流水线会验证它确实是"未签名"而不是"签名损坏"——签名损坏会让构建失败，没有签名则
如实声明。

因此 Windows 可能以两种方式提出异议：

- **SmartScreen**——"Windows 已保护你的电脑"，提示发布者无法识别。这是**信誉**
  检查，不是恶意软件判定：它触发是因为没有证书标识文件的发布者，而且来自互联网的
  文件带有 Mark of the Web 标记。
- **Microsoft Defender 或 智能应用控制**可能出于同样原因阻止或隔离该守护进程。

### 先验证，再解除阻止

不要凭信任点过安全警告。先确认你手上的字节就是已发布的字节，然后再告诉 Windows
你接受它们。

**1. 比对校验和**，与发布页面上随压缩包一同发布的 `.sha256` 文件对照：

```powershell
Get-FileHash .\zcode-cycle-<version>.zip -Algorithm SHA256
```

**2. 验证构建来源证明**——这可以证明压缩包由本仓库的发布流水线、从发布所声明的
提交构建而来，而不是由他人组装：

```powershell
gh attestation verify .\zcode-cycle-<version>.zip --repo jannotix/zcode-cycle-plugin
```

**3. 只有两项都通过后**，再移除 Mark of the Web：

```powershell
Get-ChildItem -Recurse "$env:LOCALAPPDATA\ZCode Cycle" | Unblock-File
```

在文件的**属性**对话框中也有同样的选项：在"常规"选项卡底部勾选**解除锁定**，然后
应用。

如果你直接启动某个程序时出现 SmartScreen 对话框，**更多信息 → 仍要运行**是等效的
选择。只有在完成第 1、2 步之后才使用它。

### 守护进程实际从哪里运行

Cycle 不会直接执行插件缓存中的副本。每次启动前，它都会按 `bin/native-manifest.json`
中声明的 SHA-256 校验二进制文件，然后将其复制到：

```text
<数据目录>\runtime\native\win32-x64\<二进制文件的 sha-256>\workflowd.exe
```

除非设置了 `ZCODE_CYCLE_DATA_DIR`，`<数据目录>` 为 `%LOCALAPPDATA%\ZCode Cycle`。
每个版本的摘要不同，因此会落在新的文件夹中：为某个版本做出的决定不会悄悄延续到下一个版本，
每次更新后都需要重复上述步骤。

### 如果 Defender 隔离了它

在 **Windows 安全中心 → 病毒和威胁防护 → 保护历史记录** 中恢复。如果反复被隔离，
**只**为 native 文件夹添加排除项，切勿排除整个数据目录（需要管理员权限的 PowerShell）：

```powershell
Add-MpPreference -ExclusionPath "$env:LOCALAPPDATA\ZCode Cycle\runtime\native"
```

### 如果智能应用控制（Smart App Control）阻止了它

智能应用控制没有针对单个文件的例外。处于 **开启** 状态时，它会拒绝没有信誉的未签名可执行文件，
"解除锁定"、"仍要运行"和排除项都无法改变这一点。你只能选择将其 **关闭**（在当前的 Windows 11
版本中，关闭后无法恢复，除非重置或重装 Windows），或者不在该机器上使用 Cycle。

### 受管理的机器

如果机器的安全设置由组织统一管理（Intune、组策略、WDAC/AppLocker），上述步骤可能都不可用，
本项目也不会协助绕过。请管理员按 SHA-256 哈希放行该二进制文件，哈希值发布在
`bin/native-manifest.json` 和发布版本的 `release-manifest.json` 中。

### 为什么没有证书

代码签名证书是一项与已核实法律身份绑定的持续性支出，本项目没有。签名可以消除该
警告，但并不会让这些字节比校验和与来源证明已经提供的可信度更高——这正是每个发布
都公布这两项、而本节要求你使用它们的原因。

### Windows 代码签名

内置的 `workflowd.exe` **未**经过 Authenticode 签名，今后也不会签名。首次使用时
Windows SmartScreen 会发出警告，部分终端防护软件可能将其隔离，按策略拒绝未签名
可执行文件的环境将拒绝运行它。

没有签名时仍然成立的保障：插件在 `bin/native-manifest.json` 中声明每个原生二进制
文件的 SHA-256，桥接层在启动守护进程之前校验该摘要并在不匹配时拒绝执行，二进制
文件仅以所有者可读写的权限落盘，ZCode 客户端在安装时校验归档摘要，且已封存制品
带有构建来源证明。因此完整性是可验证的；缺少的是操作系统自身的信任判定，以及文件
内部携带的发布者身份。

本项目的任何版本都不会签名：代码签名证书需要持续付费并绑定经过验证的法律身份，本项目选择不持有。上文 **Windows SmartScreen 与未签名的守护进程** 一节说明了如何校验下载内容以及如何让 Windows 运行它。

Linux 上不存在 Authenticode 的对应机制，本项目也不作此声明。那里的保障与 Windows
在没有证书时相同——执行前校验已声明的 SHA-256、安装时校验归档摘要——并额外为已封存
制品提供构建来源证明，任何人都可据此验证某个二进制文件确实由本仓库在指定提交上通过
已公开的工作流构建。Linux 守护进程在 Ubuntu 22.04 上构建，其 GLIBC 下限经校验不高于
2.35，因此在 22.04 和 24.04 上均可运行。
