# Video Creation

Choose genre, aspect ratio, duration and production method around the project goal. Standalone works and serial episodes share the asset, generation, clip-verification and editing tools; duration does not determine the workflow. For processing selected segments of existing video, combine with `video-edit-assembly`; for subtitles and speech, use `video-speech-workflows`. When assembling multiple supplied photos, clips or audio against a reference video, also read [video-edit-assembly](../video-edit-assembly/SKILL.md) and follow its reference and mix checks.

- For a standalone work, read [standalone.md](references/standalone.md): complete expression, chapter progression, scene causality and full-film effect.
- For serial episodes, read [serial.md](references/serial.md): per-episode question and payoff, pull into the next episode, character assets and cross-episode state.
- When writing a production plan or handling versions/budget, read [production.md](references/production.md). For character performance, read [performance.md](references/performance.md). For the screenplay and shot blocks, read [screenplay.md](references/screenplay.md). For a fight, struggle or chase, read [action.md](references/action.md). ## One operation, one path

Every production action that has an MCP tool is done by calling that MCP tool directly — one call per unit of work. Do not reach the same tool through the toolkit CLI (`cli/video_agent_tool.py`), through `python3`/`subprocess`, or through a batch script you write yourself, and do not substitute `ffmpeg`, `ffprobe` or an audio/vision library for a tool that exists. This covers synthesis, image and video generation, verification, timeline building, rendering and QC.

The tools and the CLI share one implementation, so a script is not wrong in its result — it is wrong in what survives. A direct call puts the arguments and the full structured result on the record, including the fields verification reads later; a script puts them behind stdout it chose to print, and whatever it prints is what anyone auditing the run can ever see. It also becomes a second place where a required argument can be dropped: on 11-03 a self-written TTS batch script was the only reason `voice_card_retries` was absent from the lines it synthesised. Batching belongs in the plan — small batches of direct calls — not in a wrapper.

Use Bash for things no tool covers: inspecting files, moving artifacts, reading logs. If a production step seems to need a script, the step is missing a tool; say so in the delivery report rather than writing around it.

## Common production method


1. From the user's brief, determine what to express, the audience, the delivery format and the materials boundary. Preserve the plot, character relationships and style the user specified. Design each scene/segment's function and the change in audience information first, then write picture and sound; structural validation cannot replace content judgment. For narrative work, write the screenplay first, segment by segment, with headings, actions and every line, and save it as `out/screenplay.md` ([screenplay.md](references/screenplay.md)); the brief is an outline, not a screenplay.
2. Cut the production plan from the screenplay: each unit names its screenplay `segment` and describes its shots as structured `blocks` (timing, framing, movement, action, line, sound), from which the prompt is compiled. New projects usually use v4 `sequences` to express a continuous performance and several viewpoints within one generation; use v2 `shots` when you need precise control of independent shots and real cuts. Estimate duration from action, measured dialogue length and editing margin; do not split evenly by a fixed number of seconds. Check the story density first: when the brief's events cannot fill the target, add pressure or deliver shorter rather than stretching, and keep narrative blocks at short-form cut rhythm ([story.md](references/story.md#density-and-pacing)).

   A unit gets music only when it declares `music` — a short cue in its own words, e.g. `"music": "低沉的古琴单音，随雨声渐入"`. Without it the generator is told to produce no music at all, which keeps dialogue clean. Declare it where music carries the work and words do not: the opening narration, an establishing or transition unit, a silent emotional beat. Leave it off a unit whose job is an exchange of lines — a bed under dialogue buys nothing and costs intelligibility. A film with no music anywhere reads as unfinished; a film with music everywhere reads as a trailer. With a generator that returns silent clips (the current one, see [generators.md](references/generators.md)) the cue is not sent: nothing comes back with sound, so music only exists as a `bgm` track the brief or the user supplies to `creation_timeline_build`; keep `music` in the plan as the record of where it belongs.
3. Check the contract with `creation_plan_validate`. It also checks the story layer (beat emotion/hook/stake, beat granularity, speaking characters' motivation, shot intent as narrative duty; see [story.md](references/story.md)) and the plan against the screenplay (segments of at most 15 s, every segment filmed, every line taken from the screenplay, blocks complete), and compiles the block prompts into the plan file. Fix every error before making cards or generating anything; generation and review refuse a plan that does not validate. Make the needed character/scene/prop cards with `image_generate`; look at the actual images, then write the final paths into the plan. Keep character cards, voice references and state cards explicitly tied to an identity. Crop the head from the original card with `image_crop` to avoid identity drift from regenerating the face.
4. Call `tts_generate` to build voice references and to generate every line of dialogue and narration — one call per line, no wrapper (see One operation, one path). Give each speaking character one fixed `voice` from the TTS service's preset voices (listed in the `tts_generate` description); omit it to use `VE_TTS_VOICE`. A cast `voice_style` is matched against those same presets. Listen to a sample and reuse the chosen ID for later dialogue; keep that sample as the character's `voice_card`. **Every `tts_generate` call must pass `voice_card`** — the character's card for a dialogue line, so the line is scored against it and a drifting synthesis is caught before any video is generated from that audio; `voice_card="none"` for a line with no character behind it (an audition, a voice card itself, a sound effect, narration owned by `narrator`). A drifting line is re-synthesised automatically: `voice_card_retries` defaults to 2 whenever a real card is given, and only a `fail` spends that budget. Pass `0` to report without repairing, or raise it to 5 for a voice that keeps slipping.

   **Write every synthesised file to these paths — they are fixed, relative to the project, and verification reads them by name:**

   | What | Path |
   | --- | --- |
   | A character's voice card | `out/creation/voice/cards/<cast_id>.wav` |
   | A shot's dialogue line | `out/creation/voice/<shot_id>_<cast_id>_<n>.wav` |
   | Voice-over / narration for a shot | `out/creation/voice/vo/<shot_id>_<owner>_<n>.wav` |
   | An audition take (choosing a voice) | `out/creation/voice/auditions/<name>.wav` |

   `<shot_id>` is the sequence id exactly as the plan spells it (`S02`, not `s02` or `S2`), and `<n>` numbers a speaker's lines within that shot from 1. Re-synthesising a line overwrites it; do not append `_v2`. Per-take verification finds a shot's own line by this name to score how far the generated speech drifted from it — a file written anywhere else is simply not found, and that check silently reports nothing.

   Voice-over sits in `vo/` and names its `<owner>`: a `cast_id` when a character narrates, or `narrator` for a voice belonging to no one in the story. It is kept out of the dialogue scan because it is laid over the cut in post and is never in the generated clip, so comparing a take's own speech to it measures nothing. Pass `voice_card` accordingly: the narrating character's card when the owner is a `cast_id`, `"none"` when the owner is `narrator`. Scoring narration against a character's card who never speaks that line on screen produces a meaningless failure.

   One character keeps one card and one `voice` for every line, and the tool checks it: a line whose path names a `cast_id` is refused when its `voice_card` or `voice` disagrees with that character's `cast[]` entry in the plan, and refused when it declares `"none"` while the plan declares a card. Verification scores the line against the plan's card, so a different card at synthesis time measures something else and the two numbers stop comparing. Change the plan's `cast[]` entry when a character's voice should change; do not pass a second card.
5. Use `video_generate` to generate candidates, each with its own `take_id`; advance in small batches and save jobs/budget. Create a new candidate when revising the prompt, references, plan or clip; when resuming the same already-submitted job, keep the original id. For local defects you may use `action=edit`; see the generator reference for supported scope.
6. Use `creation_verify action=prepare` to get each candidate's consecutive frames, voice diagnostics and plan expectations, then hand the take to a fresh judge that reads all its images and writes a verdict file: one take per judge, a fixed dispatch message, and the main agent records the verdict file unchanged with `action=record` ([verification.md](references/verification.md)). The verdict covers evidence-backed judgments for each item, the performance effect and the usable source spans. Regenerate only for the hard defects listed there; minor defects pass with a note and are cut with `usable_spans`, and a unit gets at most three regenerations. For voice, a similarity to the card at or above the scorer's `fail_below` (shown in the evidence; 0.50 for the default CAM++ scorer) passes; there is no pending voice verdict. The tool checks versions and coverage; the judge decides content. If the images were not read, required diagnostics are missing or observation is impossible, truthfully leave the status incomplete.
7. Select source spans that have a current passing review, build the shared timeline with `creation_timeline_build`, then run `timeline_validate`, `video_render kind=timeline`, `video_qc kind=video`. In-clip dialogue subtitles must use real ASR timing, never allocation by character count; when needed, after editing is finished, re-run `transcribe` and produce them with the subtitle workflow. Voiceover may span cuts; the actual audio length of the complete sentence takes priority.
8. Run `creation_review action=prepare` with the actual `render_path` to inspect every real cut and the full film. Write verdicts carrying the package/cut signature, then run `action=validate` to check current materials and coverage. Depending on the problem, reselect, edit, generate or change the plan; when the budget is exhausted, report unresolved issues - a failure cannot be treated as a pass.

9. Name a character the first time the audience sees them, and name a place the audience cannot otherwise place, with `title_cards` over the rendered cut: for example 沈紫言 (a character's name) on one line and 沈府二小姐 (her title) under it, fading in and out. Never ask the generator for text in frame — it produces characters that are not characters, and a reviewer caught exactly that in a prescription close-up. Call `action=plan` first; it writes a preview of each card drawn on the frame it will actually cover and flags a box that sits on something. **Look at every preview**, move the ones that land on a face, a hand or the prop the shot is about, then `action=render` with `placement_checked`. Two or three cards carry a short film; one per character is already too many. Dialogue is not a card — that is the subtitle workflow.

The finished film is delivered as `out/preview.mp4`: render the final cut (with subtitles, when the film has them) to that path, or copy the finished file there. The task is done only when that file exists and plays end to end; other names or copies are optional extras, and a partial cut or a still image is not a delivery. Project delivery keeps the final video, the current plan/timeline, the candidates and references used, budget and review records; output script, subtitles, series state and a short note as the user needs. State clearly the actual verification scope, remaining defects and gaps in service/observation capability.

## Candidates, review and voiceover

T18: when the original brief asks for photoreal human faces and the session already has authorization to continue, use "stylized characters with photoreal texture", mark it tentative in the plan and the delivery note (the tool records the status as the literal `暂定`), and continue directly; keep a blocker only when the original brief explicitly insists on real human faces and rejects a compatible style. Write the session's existing authorization into the plan and do not ask again; see [production.md](references/production.md#t18-tentative-handling-of-photoreal-human-requests).

T11: after keyframes, state cards and critical prop cards are generated, first bind their paths into the plan, prepare with `creation_verify action=image_prepare`, actually look at the image, then use `action=image_record` to submit `viewed:true`, the per-item observations and the verdict; move on to assembly only after confirming the record landed in the image review ledger. A successful decode does not replace content acceptance. The tool only reminds about a missing or stale confirmation, so the agent must carry out this flow itself; see [production.md](references/production.md#t11-image-viewing-confirmation).

Time discipline: once the session has run past the soft deadline (180 minutes by default), the plugin's session clock injects a reminder into the session; on receiving it, stop submitting new takes and new verification rounds, converge on delivery with the footage that has already passed review, and truthfully report the unresolved units; see [production.md](references/production.md#session-clock-and-converging-on-delivery-time-discipline). When an image is blocked by content moderation (`blocked`), follow the fallback chain in [production.md](references/production.md#fallback-discipline-for-content-blocked-images): report a blocker after at most two fallback attempts on the same asset, and do not retry in a loop.

`keyframes` in the plan automatically enter generation when the request does not specify them explicitly; an explicit request takes precedence. A resumed candidate keeps its original generation dependencies. If you changed the directing goal and want to re-evaluate existing footage, use `creation_verify action=prepare reassess=true`; this creates a review revision, keeps the original generation recipe, and states explicitly that nothing was regenerated. If reference bytes changed, restore the original file or use a new take. Treat `unavailable`/`excluded_thin` voice diagnostics as missing evidence, not as a pass. Modifying evidence images, audio or the verdict after recording a verdict blocks assembly and requires a new prepare/record. Arrange voiceover by its full measured length; when it does not fit, adjust the edit or the lines - never silently truncate the tail.
