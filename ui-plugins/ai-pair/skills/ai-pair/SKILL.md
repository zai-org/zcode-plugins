# AI Pair 评审工作流

你（主对话 agent）负责把待评审材料提交给 ai-pair 插件，并如实转达评审结果。评审本身
由插件的 MCP server 调用用户在 ZCode 里配置的两个模型渠道完成——你**不需要也不能**
自己扮演评审员。

## 工具清单

- `request_review`：提交评审（见下）
- `get_review {id}`：取回完整报告
- `list_reviews`：列历史评审
- `delete_review {id}` 或 `{all:true}`：删除单条/清空评审记录（用户说"删掉这条评审/清空评审记录"时调用；进行中的任务不可删）
- `open_panel`：打开「AI Pair 评审」侧栏面板。用户说"打开评审面板""打开 AI Pair"时立即调用
- `list_models`：列出 ZCode 全部渠道与模型，并实测两个评审位的连通性
- `configure_reviewers {reviewer1:{channel,model}, reviewer2:{channel,model}, cross}`：
  级联选择评审位的渠道+模型，立即生效。用户说"评审模型 1 用 Kimi 的 k3.1-pro"这类话时调用。
  channel 填渠道名或 ID；某槽位不传表示清除该位选择。**绝不未经用户确认就自动选渠道。**

## 何时使用

- 用户说"送 ai-pair 评审"、"让两个模型看看"、"双模型评审一下"
- 用户要求质量把关：重构、安全相关改动、发布前检查、重要文章定稿前

## 流程

1. **提交评审**：调用 `request_review` 工具：
   - `title`：一句话说明改了什么
   - `focus`：代码改动用 `dev`，文章/文案用 `content`
   - `diff`：本次改动的 diff（优先；可用 git diff 生成）
   - `files`：或提供工作区内相对路径列表（服务端读取全文）
   - `notes`：给评审员的背景与关注点（可选但建议提供）
   - `cross`：交叉质证轮开关。用户说"要交叉质证/互相复核"时传 true，"不用质证"传 false；
     不传则按面板设置里的默认值。开启后渠道 token 约翻倍，需先告知用户
   - 默认立即返回任务 id，评审后台运行（通常 1-3 分钟；启用质证约 3-6 分钟）
2. **等待与取回**：
   - 用户可打开侧栏「AI Pair 评审」面板实时查看
   - 完成后调用 `get_review(id)` 取回完整报告，向用户总结：
     两份报告的共识问题、各自独有的发现、冲突之处（如实并列，交用户裁决）；
     若有交叉质证轮，优先转述 [WRONG]/[MISS] 项——那是最可能有价值的发现
   - 评审未完成时不要轮询刷屏；告知用户面板会自动刷新，或稍后再取
3. **后续**：用户决定是否按 CRITICAL → WARNING → SUGGESTION 的顺序修改；
   修改后可再次提交评审形成新的一轮

## 配置与排障

- `list_models`：列出 ZCode 全部渠道与模型，并实测两个槽位的连通性。
  为评审位选渠道/模型前先跑它，把渠道名/模型 ID 照抄给用户。
- 某个槽位评审失败时如实告知原因（常见：未选渠道、模型 ID 不在渠道里、渠道鉴权失败），
  不要自己补写"评审意见"。

## 规则

- 两位评审员是固定分工（角色由插件注入提示词，不随渠道变化）：
  评审模型 1 · **正确性把关**（代码偏 bug/安全/边界，内容偏事实与逻辑），
  评审模型 2 · **设计与可维护性**（代码偏架构/可读性，内容偏结构/风格/受众）；
  结论冲突时不要替用户做决定，并列呈现
- CRITICAL 项建议优先处理，但处理与否由用户决定
